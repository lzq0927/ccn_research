# OpenClaw vs Hermes：一个案例看穿Harness四步法

> 编制日期：2026-06-06
> 方法：各选一个最典型的实战案例，按合并后的Harness四步走，好的差的都讲

---

## 为什么七步合并为四步

原Harness七阶段（初始化→前馈引导→拦截执行→自纠正→验证门控→状态持久→持续演进）覆盖全面，但叙事和实践中存在自然的两两配对：

| 原七步 | 合并 | 合并理由 |
|--------|------|---------|
| S1 初始化 + S2 前馈引导 | **准备（Prepare）** | 都是"执行前的事"——一个设边界，一个灌知识 |
| S3 拦截执行 | **执行（Execute）** | Agent实际干活的核心环节，无法归并 |
| S4 自纠正 + S5 验证门控 | **验证（Validate）** | 都是"检查对不对"——一个是边做边查，一个是做完总查 |
| S6 状态持久 + S7 持续演进 | **进化（Evolve）** | 都是"用完之后的事"——一个是记住经验，一个是从经验中学习 |

合并后的四步形成一个清晰的循环：

```
┌──────────┐     ┌──────────┐     ┌──────────┐     ┌──────────┐
│  准备     │────▶│  执行     │────▶│  验证     │────▶│  进化     │
│ Prepare  │     │ Execute  │     │ Validate │     │ Evolve   │
└──────────┘     └──────────┘     └──────────┘     └──────────┘
      ▲                                                  │
      └──────────────────── 闭环反馈 ◄───────────────────┘
```

## 案例一：OpenClaw — Context Studios "Timmy"

**背景**：柏林一人内容工作室，Mac Mini 24/7运行OpenClaw Agent "Timmy"，挂载134个MCP工具。Timmy每天自动发布4语言博客、制作视频短片、管理社交媒体、监控网站心跳——**把一个人变成了一支5-8人的内容团队**，月API成本仅$200-500。

来源：[Context Studios - Complete OpenClaw Guide](https://www.contextstudios.ai/blog/the-complete-openclaw-guide-how-we-run-an-ai-agent-in-production-2026)

---

### 第1步：准备（Prepare）

**初始化做得怎样**：

Timmy的部署是典型的"个人开发者体验"——Docker一键启动，5分钟跑起来。但这恰恰是问题所在：

- **没有权限清单**：Timmy拿到了操作Mac Mini上几乎所有工具的权限——Shell执行、浏览器自动化、文件读写、CMS发布、社交媒体登录。没有任何显式的Permissions Manifest来约束"Timmy不该做什么"。
- **没有沙箱隔离**：Timmy直接运行在宿主机上，不是Docker沙箱。一次工具调用的Bug或被注入的恶意指令可以影响整台机器。
- **没有任务分解**：Timmy同时负责内容创作、SEO、翻译、CMS、社交媒体、视频合成、心跳监控——这些是完全不同的领域，但没有拆分为独立子任务或子Agent。

**前馈引导做得怎样**：

这是OpenClaw真正强的地方。134个MCP工具构成了极其丰富的"操作手册"：

- ClawHub技能市场提供了预置的工作流模板（博客发布流水线、视频合成流水线）
- 动态System Prompt为不同任务注入上下文
- 向量嵌入语义搜索让Agent能快速定位相关的历史经验
- MEMORY.md记录了工作室的品牌调性、常用模板、发布偏好

**效果**：工具生态的丰富性是Timmy能一人顶一个团队的根本原因。从选题到发布到SEO到社交分发，每个环节都有对应的MCP工具无缝衔接。

**缺失**：前馈引导虽然丰富，但ClawHub技能有12%是恶意的（ClawHavoc供应链攻击审计了2857个技能发现341个恶意）。Timmy的134个工具中是否每个都经过源码审查？用户没有提及。

> **准备步小结**：OpenClaw的"上手5分钟"是双刃剑——快是快了，但权限、沙箱、任务分解全都没有。134个MCP工具是杀手锏，但供应链安全是定时炸弹。

---

### 第2步：执行（Execute）

**这是Timmy整个案例中最精彩的部分。**

OpenClaw的四层Hub-Spoke架构在这个场景中发挥了最大价值：

- **多平台接入**：Timmy通过统一的Channel Adapter层对接WordPress CMS、X/LinkedIn/Facebook API、Google Search Console、ElevenLabs、Veo 3.1等20+服务，所有平台的消息格式被统一为内部标准格式
- **工具编排流畅**：博客发布流水线（研究→写作→翻译→SEO→CMS发布→配图→URL验证→GSC提交→社交分发）一气呵成，没有人工干预
- **视频流水线**：20+工具的编排（Veo 3.1场景→ElevenLabs语音→Sync Labs口型同步→自动字幕→合成）同样全自动
- **浏览器自动化**：Timmy甚至能登录LinkedIn、切换到公司主页身份、浏览帖子并留下评论——这展示了OpenClaw的CDP（Chrome DevTools Protocol）能力

**效果**：

| 流水线 | 工具数 | 自动化程度 |
|--------|--------|-----------|
| 4语言博客发布 | ~15个MCP工具 | 全自动，零人工 |
| 视频短片制作 | 20+个MCP工具 | 全自动，零人工 |
| 社交媒体管理 | ~5个MCP工具 | 全自动，含浏览器自动化 |
| 心跳监控 | ~4个MCP工具 | 24/7，仅异常时告警 |

**缺失**：执行层没有拦截验证。Timmy调用工具是"直通"的——Shell命令直接执行，CMS直接发布，社交媒体直接发帖。没有Tool Gate来验证参数合理性，没有ConfirmationStrategy来区分"读操作自动通过、写操作需确认"。CVE-2026-25253（CVSS 8.8，一键远程代码执行）说明这个"直通"模式在安全上有多脆弱。

> **执行步小结**：工具编排能力惊艳，134个MCP工具串联出的流水线是一人工作室的核武器。但"直通执行"意味着一旦出问题（模型幻觉、Prompt注入、恶意工具），后果没有缓冲。

---

### 第3步：验证（Validate）

**这是Timmy案例中最薄弱的环节——几乎为零。**

**自纠正机制**：无。OpenClaw没有内置的幻觉检测、输出验证或环检测。如果Timmy发布的博客内容有事实错误，没有机制能在发布前拦截。

**验证门控**：只有可选的工具确认提示（用户可以关闭），以及基本的JSONL会话日志。

**实际风险**：
- **内容质量完全依赖模型能力**：4语言翻译的准确性、SEO关键词的合理性、社交媒体评论的得体性——全部没有交叉验证
- **浏览器自动化的安全风险**：Timmy可以登录LinkedIn并代为评论。如果遭遇Prompt注入（Zenity研究已证明可行——通过Google Doc隐藏指令让OpenClaw创建Telegram后门），后果不堪设想
- **供应链盲区**：134个MCP工具中如果有恶意工具，没有任何机制检测

**用户的实际应对**：Context Studios没有提及任何验证机制。这暗示他们可能采取了"快速发布、事后人工抽查"的策略——对内容创作可以接受，但对核心网运维**完全不可接受**。

> **验证步小结**：这是OpenClaw的致命短板。在内容创作场景，发一篇有瑕疵的博客可以事后改；但在核心网场景，一次未验证的操作可能导致全网故障。**缺少验证的Agent越强大，出事时后果越严重。**

---

### 第4步：进化（Evolve）

**状态持久化做得怎样**：

MEMORY.md + 向量嵌入搜索 + 每日笔记构成了基本可用的记忆系统。Timmy能记住工作室的品牌调性、常用模板和发布偏好，跨会话保持一致性。

**持续演进做得怎样**：

**这是OpenClaw的第二个致命短板——没有自进化。** Timmy用了100次和用了1次，能力没有任何区别。Agent不会从"某篇博客反响好"中学习应该多写什么主题，也不会从"某次翻译质量差"中学习改进翻译策略。

**对比效应**：如果用Hermes替代OpenClaw运行Timmy，理论上：
- 第10次发布后，Agent学会了哪种标题在哪个语言市场转化率高
- 第50次发布后，Agent自动积累了"德语区用户偏好技术细节而非营销话术"的技能
- 第100次发布后，Agent的内容质量显著优于第1次

但用OpenClaw，第1次和第100次完全一样。

> **进化步小结**：记忆系统基本够用，但缺少自进化意味着"经验资产在流失"——Timmy每天产生的大量内容创作经验，没有被编码为可复用的技能。

---

### Timmy案例四步总评

| 步骤 | 评分 | 关键词 |
|------|------|--------|
| 准备 | ★★★☆☆ | 上手快但无边界，工具丰富但供应链有风险 |
| 执行 | ★★★★☆ | 134工具编排惊艳，但直通执行无缓冲 |
| 验证 | ★☆☆☆☆ | **几乎为零**，内容创作可承受，核心网不可承受 |
| 进化 | ★★☆☆☆ | 记忆可用但不进化，经验无法增值 |

**一句话**：Timmy是一个"第一天很惊艳，第一百天还一样"的Agent。

## 案例二：Hermes Agent — heyuan110一周深度体验

**背景**：独立开发者heyuan110在$5/月Hetzner VPS上运行Hermes Agent一周，同时对比使用Claude Code和OpenClaw。他的体验成为Hermes社区最广为流传的真实用户报告。

来源：[heyuan110 - Hermes Agent Guide](https://www.heyuan110.com/posts/ai/2026-04-14-hermes-agent-guide/)

---

### 第1步：准备（Prepare）

**初始化做得怎样**：

比OpenClaw复杂，但**刻意为之**：

- **子Agent隔离是默认配置**：每个子Agent通过`register_task_env_overrides()`请求独立沙箱。heyuan110运行了多个子Agent（代码审查、研究助手、日常任务），它们完全隔离——一个Agent的崩溃不影响其他Agent
- **聚焦上下文窗口**：每个子Agent只看到与当前任务相关的信息，不是把所有历史塞进来。这减少了"上下文溢出幻觉"
- **成本极低**：$5/月VPS + 可选Gemini Flash Lite（$0.02/次），对比OpenClaw的$200-500/月

**前馈引导做得怎样**：

Hermes没有134个MCP工具的丰富生态，但它做了两件OpenClaw没做的事：

- **`/goal`目标锁定**：用户设定Agent的长期目标后，Agent在整个运行过程中持续对齐该目标。对于长时间运行的任务（如跨天的代码审查、跨周的研究项目），这防止了"上下文漂移"——Agent不会在运行到第3个小时时忘了最初要干什么
- **FTS5全文检索**：跨会话记忆不是简单地把历史塞进上下文窗口，而是用SQLite FTS5索引按需检索相关历史。这意味着上下文窗口里只有真正相关的信息

**效果**：heyuan110的体验是"比Claude Code慢上手，但比OpenClaw安全"。配置花了更多时间，但运行后更稳定。

**缺失**：per-subagent资源限制尚未完成（Issue #4271开发中）。一个失控的子Agent理论上可能耗尽系统资源。对于$5/月的VPS，这意味着需要手动监控。

> **准备步小结**：Hermes的初始化慢于OpenClaw，但**安全默认值更强**。子Agent隔离 + 聚焦上下文 + 目标锁定——这三件事OpenClaw一样都没做。

---

### 第2步：执行（Execute）

**Hermes的执行模式和OpenClaw有本质区别**：

OpenClaw是"直通执行"——工具调用直接执行，没有中间层。Hermes是"隔离执行"——每个子Agent在独立沙箱中运行，输入输出都是隔离的。

**实际体验**：

- **子Agent并行**：heyuan110同时运行代码审查Agent和研究助手Agent，两者完全独立，互不干扰。对比OpenClaw的Timmy是一个单体Agent处理所有任务
- **上下文聚焦**：代码审查Agent只看到代码相关的上下文，不会因为研究助手的历史而分心。这减少了无关信息干扰导致的幻觉
- **Checkpoint机制**：执行破坏性文件操作前，自动创建文件系统快照。如果Agent改坏了代码，可以回滚到上一个检查点

**效果**：heyuan110没有给出具体的效率数字，但描述了一个关键体验差异——"Hermes不会因为一个任务的失败影响另一个任务"。在一次代码审查Agent遇到困难时，研究助手Agent继续正常运行。

**对比OpenClaw Timmy**：Timmy的134工具编排能力是Hermes不具备的。Hermes的工具生态远不如OpenClaw丰富（没有20+平台的Channel Adapter、没有视频合成流水线）。**在"工具数量"上OpenClaw完胜，在"执行安全性"上Hermes完胜。**

> **执行步小结**：Hermes的执行不如OpenClaw"花哨"，但更"稳"。子Agent隔离天然具备拦截语义——每个子Agent的输入输出都经过边界。对于核心网场景，"稳"比"花哨"重要得多。

---

### 第3步：验证（Validate）

**这是Hermes与OpenClaw的决定性差距所在。**

**幻觉门控（Hallucination Gate）**：

Hermes在Agent输出传播到下游之前设置验证检查点。如果一个子Agent的输出未通过验证，任务被退回并附上原因，而不是标记为"完成"后继续传递。

- **解决什么问题**："静默腐败"——在多Agent管道中，一个Agent的错误输出如果不经验证就传给下游，错误会级联放大。感知Agent错了→分析Agent基于错误信息分析→执行Agent基于错误分析操作——每一步都在放大错误
- **实际效果**：heyuan110没有给出幻觉拦截率的数字（公开资料中也没有找到量化数据），但描述了一个可感知的体验差异——"Hermes的输出比其他Agent更'干净'，不会出现自信地陈述错误信息的情况"

**Ralph Loop（韧性循环）**：

当Agent遇到困难时，不是直接报错退出，而是持续尝试不同策略。

- **解决什么问题**："过早放弃"——Agent在遇到困难时倾向于简单报错退出而非尝试其他方法
- **实际效果**：heyuan110描述了代码审查Agent遇到一个复杂Bug的场景——第一次分析失败后，Agent自动换了一个策略（从静态分析切换到运行测试复现），第二次成功了

**缺失（需要实事求是说）**：

1. **幻觉门控是启发式的，非形式化证明**：它比OpenClaw的"零验证"强得多，但不如Datadog推荐的DST确定性仿真测试。幻觉门控不能保证100%拦截所有幻觉
2. **没有公开的量化数据**：没有"幻觉拦截率X%、误报率Y%"这样的数字。GitHub Issue #688甚至提到"Hermes目前没有内置的幻觉检测机制"——这暗示"幻觉门控"可能更多是一个验证/检查点工作流，而非真正的幻觉检测系统
3. **缺少人机确认层**：对于高危操作（如生产环境部署），没有内置的"必须人工确认"机制

> **验证步小结**：Hermes有验证，OpenClaw没有——这是质的差距。但Hermes的验证不是完美的：启发式而非形式化、缺乏量化数据、缺少人机确认层。对核心网场景，需要在Hermes的基础上**再叠加**Datadog DST和人机确认。

---

### 第4步：进化（Evolve）

**这是Hermes最独特的体验，也是heyuan110报告中最打动人的部分。**

**Closed Learning Loop的实际体验**：

heyuan110描述了一个令人印象深刻的变化过程：

> "By the tenth time, everything has changed. It knows you prefer httpx over requests. It knows you like error logs written to files. Nobody taught it these. It learned on its own."

翻译：到第10次交互时，一切都变了。它知道你更喜欢httpx而不是requests，它知道你喜欢把错误日志写入文件。没有人教过它这些，它是自己学会的。

**学习机制**：

1. 每次任务执行后，Agent自动提取经验
2. 如果检测到反复出现的模式，自动创建一个"Skill"（技能文件）
3. 下次遇到类似任务时，通过FTS5全文检索自动加载相关技能
4. 如果已有技能在实际使用中发现不合适，自动修改技能

**底层技术**：DSPy + GEPA（Genetic-Pareto Prompt Evolution）——ICLR 2026 Oral论文（MIT），通过API调用实现自动进化，不需要GPU。

**OpenRouter #1的验证**：Hermes在2026年5月10日以2240亿token/天超越OpenClaw（1860亿），成为全球使用量最大的Agent框架。用户用脚投票——如果自进化只是噱头，不会有这么多人持续使用。

**缺失（同样实事求是）**：

1. **自进化不是完全自动的**：一篇Medium评论指出"self-improving seems exaggerated——you have to explicitly tell Hermes to retain information and create a skill"。某些情况下需要用户主动触发技能创建
2. **没有公开的纵向改进曲线**：DSPy+GEPA系统会生成内部报告，但没有公开的时间序列数据（如"第1周准确率X%，第4周准确率Y%"）
3. **审计复杂度高**：技能是Agent自修改的，对需要SOC2审计的企业场景，自修改增加了追溯难度

> **进化步小结**：这是Hermes与OpenClaw的根本代差。heyuan110的原话——"你无法回到没有它的日子"——不是对某个功能的赞美，而是对一种全新体验的描述：**第一次有了一个真正"记住你"的Agent。** 但自进化在自动化程度和审计可追溯性上仍有提升空间。

---

## 两个案例的对照结论

### 四步法对照表

| Harness步骤 | OpenClaw Timmy | Hermes heyuan110 | 决定性差距 |
|------------|----------------|-------------------|-----------|
| **准备** | 上手5分钟但无边界 | 配置稍慢但安全默认 | 安全 vs 便捷 |
| **执行** | 134工具惊艳但直通 | 工具少但隔离执行 | 花哨 vs 稳健 |
| **验证** | ★☆☆☆☆ 几乎为零 | ★★★★☆ 有门控但非完美 | **有无之别** |
| **进化** | ★★☆☆☆ 记忆但不进化 | ★★★★★ 自进化闭环 | **能力代差** |

### 两个核心发现

**发现一：验证是分水岭**

Timmy没有验证，但运行得很好——因为内容创作的容错率高，发错一篇博客可以改。heyuan110有验证，而且感受到了实际效果——输出更"干净"、Agent更"韧"。

在核心网场景，验证不是"锦上添花"而是"生死线"。一个没有验证的Agent越强大（像Timmy这样134工具全自动化），出事时后果越严重。

**发现二：进化是护城河**

heyuan110一周的体验已经能感知到自进化的差异。想象如果运行6个月——Agent对用户偏好的理解、对项目上下文的积累、对常见问题的应对——这些是OpenClaw永远无法积累的资产。

这正好印证了Harness Engineering的核心论点：**同一个模型，不同的Harness，长期效果天壤之别。** OpenClaw和Hermes背后可能是同一个底层模型，但Hermes的Harness（幻觉门控+Ralph Loop+Closed Learning Loop）让它在第10次交互时已经拉开了质的差距。
