## 二、核心架构

Hermes的核心架构与OpenClaw的"大一统Hub"模式不同，采用**多模型协作推理 + 子Agent并行**的分布式架构。

```
┌─────────────────────────────────────────┐
│            Hermes 核心架构               │
├─────────────────────────────────────────┤
│                                         │
│  ┌──────────┐  ┌──────────┐            │
│  │ 子Agent A │  │ 子Agent B │  ...       │
│  │(独立沙箱) │  │(独立沙箱) │            │
│  │聚焦上下文 │  │聚焦上下文 │            │
│  └─────┬────┘  └─────┬────┘            │
│        │              │                 │
│  ┌─────▼──────────────▼─────────────┐  │
│  │   幻觉门控 (Hallucination Gate)   │  │
│  │   检测并过滤幻觉，阻止级联传播     │  │
│  └──────────────┬───────────────────┘  │
│                 │                       │
│  ┌──────────────▼───────────────────┐  │
│  │   自进化学习循环                   │  │
│  │   执行→经验→技能→复用→提升        │  │
│  └──────────────────────────────────┘  │
└─────────────────────────────────────────┘
```

## 三、三大核心特性详解

### 3.1 Hallucination Gate（幻觉门控）

**这是Hermes最核心的差异化创新。**

- **问题**：在多Agent管道中，一个Agent的错误输出如果不经验证就传递给下游Agent，会导致"**静默腐败**（Silent Corruption）"——错误在管道中级联放大，每个后续Agent都基于错误信息做出决策
- **解决**：在Agent输出传播到下游之前，设置**验证检查点（Verification Checkpoint）**
- **效果**：检测并过滤幻觉输出，阻止错误信息在多Agent管道中级联放大
- **对核心网的意义**：故障诊断场景中，感知Agent的错误判断如果未经门控就传递给分析Agent，可能导致错误的根因定位；分析Agent的错误传递给执行Agent，可能导致错误的网络操作。幻觉门控在传播链中设置"检查站"，**极大降低级联故障风险**

### 3.2 /goal Command（目标锁定）

- **问题**：长时间运行的Agent容易出现"**上下文漂移（Context Drift）**"——随着对话历史增长，Agent逐渐遗忘初始目标，产生与目标无关甚至矛盾的行为
- **解决**：用户通过`/goal`命令设定Agent的长期目标，Agent在整个运行过程中持续对齐该目标
- **效果**：防止Agent在长时间运行中偏离预定任务
- **对核心网的意义**：核心网运维Agent通常需要长时间运行（如故障巡检可能持续数小时、容量规划可能持续数天），目标锁定防止Agent偏离预定任务

### 3.3 Ralph Loop（韧性循环）

- **问题**：Agent在遇到困难时倾向于**过早放弃（Premature Quitting）**——简单报错退出而非尝试其他方法
- **解决**：通过循环机制，当Agent遇到困难时不是退出，而是持续尝试不同策略
- **效果**：提高任务完成率，减少Agent的无效终止
- **命名来源**：与OpenAI Codex团队使用的"Ralph Wiggum Loop"理念相同——Agent审查自己的结果，不满意就重试

## 四、Sub-Agent Isolation（子Agent隔离）

### 4.1 实现机制

- 子Agent通过`register_task_env_overrides()`请求独立的隔离沙箱
- 每个子Agent使用**聚焦的上下文窗口（Focused Context Window）**
- 上下文窗口仅包含与当前子任务相关的信息，不包含父Agent或其他子Agent的历史

### 4.2 效果

- **减少上下文溢出幻觉**：上下文窗口小而聚焦，模型不需要处理无关信息
- **防止级联故障**：一个子Agent的失败不会影响其他子Agent
- **并行执行**：多个子Agent可以同时处理不同子任务

### 4.3 发展中能力

- **Issue #4271**：正在开发per-subagent资源限制（CPU/内存配额）
- 当前风险：一个失控的子Agent可能耗尽系统资源，影响其他子Agent

## 五、Closed Learning Loop（自进化学习循环）

### 5.1 循环流程

```
任务执行(Task Execution)
    → 经验提取(Experience Extraction)
    → 技能创建/改进(Skill Creation/Improvement)
    → 技能复用(Skill Reuse)
    → 效率提升(Efficiency Gain)
    → 反馈到任务执行 ↑
```

### 5.2 关键机制

- Agent从每次任务执行中**自动提取经验**
- 将经验编码为可复用的**"技能"（Skill）**
- 后续遇到类似任务时，自动加载并应用已有技能
- 随着使用时间增长，Agent在特定领域的准确性和效率**持续提升**

### 5.3 核心价值

- **经验资产化**：运维经验不再只存在于运维人员脑中，而是被编码为Agent技能
- **越用越准**：不同于OpenClaw的"每次从零开始"
- **领域适配**：不同团队使用同一个Hermes实例，会因为经验不同而形成不同的领域专长

## 六、Harness Engineering能力评估

| Harness维度 | Hermes实现 | 评价 |
|------------|-----------|------|
| **内存管理** | 技能存储（结构化、可复用） | 优于OpenClaw的MEMORY.md |
| **工具编排** | 多模型协作推理 | 灵活但平台覆盖不如OpenClaw |
| **安全护栏** | 子Agent隔离 + 资源限制（开发中） | 隔离性好，但per-subagent限制未完成 |
| **验证机制** | 幻觉门控（内置验证检查点） | **核心优势**，OpenClaw没有 |
| **可观测性** | 基础日志 | 不如Datadog式的全链路可观测 |
| **自纠正** | 幻觉门控 + Ralph Loop | **行业领先** |
| **自进化** | Closed Learning Loop | **行业领先**，让经验增值 |

## 七、框架评价

### 优势
- **幻觉门控是核心网的关键能力**：直接解决级联错误传播问题
- **自进化让经验增值**：运维经验被编码为技能，越用越准
- **子Agent隔离防止级联故障**：不同网络域的Agent独立运行
- **目标锁定防止漂移**：长时间运维任务不偏离
- **Ralph Loop提高韧性**：不因暂时困难放弃任务

### 不足
- **上手比OpenClaw复杂**：配置和理解成本更高
- **per-subagent资源限制尚未完成**（Issue #4271）：存在资源争用风险
- **缺少Datadog式的形式化验证**：幻觉门控是启发式的，非数学证明
- **可观测性不够深度**：缺少全链路遥测和异常检测

**结论**：Hermes在Harness Engineering的核心能力（幻觉门控、自纠正、自进化）上**显著领先OpenClaw**，更适合核心网等高可靠性工业场景。但需要补充形式化验证层（参考Datadog DST）和全链路可观测（参考OpenTelemetry）。
