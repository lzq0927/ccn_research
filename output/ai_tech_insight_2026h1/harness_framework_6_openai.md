# OpenAI (Codex) -- 百万行代码零手写的 Harness Engineering 实践框架

> 来源: https://openai.com/index/harness-engineering/

## 一、背景与规模

OpenAI 的这篇文章可能是2026年最具影响力的 Harness Engineering 实践报告。一个 **3人团队**(后扩展至7人),在 **5个月**内,使用 Codex 构建了一个约 **100万行代码** 的内部软件产品,实现了 **~1,500 merged PRs**,平均 **3.5 PRs/engineer/day**——最引人注目的是:**0 行手写代码**。

核心哲学:"**Humans steer. Agents execute.**"人类转向设计环境、指定意图、构建反馈循环,而 Agent 负责执行。

## 二、7步实践生命周期

### 步骤 1: 空 Git 仓库 + Agent 生成脚手架

2025年8月底,第一次提交到一个空仓库。初始脚手架——仓库结构、CI 配置、格式化规则、包管理器设置和应用框架——由 Codex CLI 使用 GPT-5 生成,以少量现有模板为指导。连指导 Agent 如何在仓库中工作的 `AGENTS.md` 文件本身也是由 Codex 编写的。

没有预先存在的手写代码来锚定系统。从一开始,仓库就由 Agent 塑造。

### 步骤 2: 深度优先能力构建

早期进展比预期慢,不是因为 Codex 无能力,而是因为**环境规格不足**。Agent 缺乏向高层目标推进所需的工具、抽象和内部结构。

工程团队的首要工作变成了**使 Agent 能够做有用的事**。实践方法是深度优先(Depth-first):将较大目标分解为更小的构建块(设计、编码、审查、测试等),提示 Agent 构建这些块,然后用它们解锁更复杂的任务。

当某件事失败时,修复几乎从不是"再努力"。因为唯一取得进展的方式是让 Codex 做工作,工程师总是进入任务并问:"缺少什么能力,如何使其对 Agent 既可理解又可执行?"

### 步骤 3: 渐进式上下文披露

Context Management 是最大的挑战之一。最早的教训之一很简单:**给 Codex 一张地图,而不是一本1000页的说明书。**

四个原因:
1. **上下文是稀缺资源**: 巨大的指令文件挤占了任务、代码和相关文档
2. **过多指导变成无指导**: 当一切都是"重要"的,什么都不是。Agent 最终在局部模式匹配而非有意导航
3. **它立即腐烂**: 单一大块文档变成陈旧规则的坟墓
4. **难以验证**: 单一 Blob 不便于机械检查(覆盖度、新鲜度、所有权、交叉链接)

解决方案:将 `AGENTS.md` 视为**目录**,而非百科全书。仓库知识库存在于结构化的 `docs/` 目录中。一个约100行的 `AGENTS.md` 注入上下文,主要作为带有指向其他地方更深层真相指针的地图。

这实现了**渐进式披露(Progressive Disclosure)**:Agent 从一个小而稳定的入口点开始,被教导下一步看哪里,而不是预先被淹没。

### 步骤 4: 架构机械强制

每个业务领域被划分为固定的层集合,具有严格验证的依赖方向和有限的可允许边:

```
Types -> Config -> Repo -> Service -> Runtime -> UI
```

横切关注点(auth、connectors、telemetry、feature flags)通过单一显式接口 **Providers** 进入。其他一切都不被允许,并通过自定义 Linter 机械强制执行。

这些 Linter 是 Codex 生成的,错误消息被特别设计为**将修复指令注入 Agent 上下文**——每次失败消息都成为下一次尝试的上下文。加上"Taste Invariants":静态强制结构化日志、Schema 和类型的命名约定、文件大小限制、平台特定可靠性要求。

### 步骤 5: Agent-to-Agent 审查

人类通过 Prompt 与系统交互:描述任务、运行 Agent、让其打开 PR。驱动 PR 完成的流程:

1. Codex 在本地审查自己的变更
2. 请求额外的特定 Agent 审查(本地和云端)
3. 响应人类或 Agent 给出的反馈
4. 迭代循环直到所有 Agent 审查者满意

这实质上是 **Ralph Wiggum Loop**——一个 Agent 持续自我审查和改进的循环。

人类可以审查 PR,但**不被要求这样做**。随着时间推移,几乎所有的审查工作都被推向 Agent-to-Agent。

### 步骤 6: 持续 GC 清理 (Garbage Collection)

完全的 Agent 自治引入了新问题:**Codex 复制仓库中已存在的模式——甚至是不均匀或次优的模式**。随时间推移,这不可避免地导致漂移。

最初,人类手动处理,每周五(一周的20%)清理"AI slop"。不可扩展。

解决方案:编码"Golden Principles"到仓库中并构建**定期清理流程**。原则示例:
- 偏好共享工具包而非手写辅助函数,保持不变量集中
- 不"YOLO-style"探测数据——验证边界或依赖类型化 SDK

在常规节奏下,一组后台 Codex 任务扫描偏差、更新质量等级并打开有针对性的重构 PR。大多数可以在一分钟内审查并自动合并。

**功能类比:垃圾回收。技术债如同高息贷款——几乎总是以小增量持续偿还好于让它复利并在痛苦爆发中处理。人类品味被捕获一次,然后在每行代码上持续执行。**

### 步骤 7: 全自动功能交付

仓库最近越过一个有意义的阈值:给定单个 Prompt,Codex 可以端到端驱动一个新功能:

1. 验证代码库当前状态
2. 复现报告的 Bug
3. 录制展示失败的视频
4. 实现修复
5. 通过驱动应用验证修复
6. 录制展示解决的视频
7. 打开 Pull Request
8. 响应 Agent 和人类反馈
9. 检测和修复构建失败
10. 仅在需要判断时升级给人类
11. 合并变更

## 三、关键机制

### 3.1 Per-worktree App Booting

应用可按 Git Worktree 启动,使 Codex 能为每个变更启动和驱动一个独立实例。每个 Worktree 拥有完全隔离的应用版本——包括其日志和指标,在任务完成后被销毁。

### 3.2 Chrome DevTools Protocol

将 Chrome DevTools Protocol 接入 Agent 运行时,创建用于处理 DOM 快照、截图和导航的 Skills。使 Codex 能直接复现 Bug、验证修复并推理 UI 行为。

### 3.3 本地可观测性栈

日志、指标和追踪通过临时的本地可观测性栈暴露给 Codex。Agent 可以用 LogQL 查询日志、用 PromQL 查询指标。诸如"确保服务启动在800ms内完成"或"这四个关键用户旅程中没有任何 Span 超过两秒"这样的 Prompt 变得可行。

### 3.4 分层架构强制

约束在中心强制执行,在本地允许自主。关注边界、正确性和可复现性。在边界内,允许 Agent(或团队)在解决方案表达上享有显著自由。

### 3.5 Taste Invariants (品味不变量)

小而关键的"品味"规则集,通过自定义 Lint 静态强制执行。当文档不足时,将规则提升为代码。人类品味持续反馈:审查评论、重构 PR 和面向用户的 Bug 被捕获为文档更新或直接编码到工具中。

### 3.6 Linter 错误消息作为上下文

自定义 Lint 的错误消息被特别设计为注入修复指令到 Agent 上下文中。**每一次失败消息都成为下一次尝试的学习材料**——OpenAI 认为这是一种"正向的 Prompt Injection"。

### 3.7 Doc-gardening Agent

一个定期运行的 Agent 扫描过时或废弃的文档(不反映真实代码行为),并打开修复 PR。文档的"园艺"与代码的维护同等重要。

## 四、生产洞察

### 4.1 "无聊"技术优先

技术选择偏好那些在训练集中有良好代表性、API 稳定、可组合性强的"无聊"技术。在某些情况下,让 Agent 重新实现功能子集比应对上游不透明行为更便宜。例如,实现自己的 map-with-concurrency 辅助函数而非使用 `p-limit` 包。

### 4.2 纠正成本低于等待成本

仓库以最少的阻塞合并门控运行。PR 生命周期短。测试 Flaky 常通过后续运行解决而非无限阻塞进展。在 Agent 吞吐量远超人类注意力的系统中,纠正廉价,等待昂贵。

### 4.3 Agent Legibility (Agent 可读性) 是目标

从 Agent 的角度看,任何它运行时无法在上下文中访问的东西**实际上不存在**。存在于 Google Docs、聊天线程或人们脑海中的知识对系统不可访问。仓库本地、版本化的工件(代码、Markdown、Schema、可执行计划)是它能看到的一切。

## 五、框架评价

### 优势

- **最极端的实践验证**: 100万行代码、1500 PRs、0手写代码——这是目前公开的最极端的 Harness Engineering 实践案例。
- **7步生命周期可操作**: 从空仓库到全自动功能交付的完整路径,每一步都有具体的机制和工具支撑。
- **Linter 错误消息即上下文**: 这是一个被低估但极其精妙的实践——将失败转化为学习机会,使 Harness 成为"自愈系统"。
- **GC 清理机制创新**: 将技术债管理类比为垃圾回收,从被动修复转向主动预防。
- **吞吐量哲学**: "纠正成本低于等待成本"颠覆了传统代码审查的低吞吐量哲学。

### 不足

- **模型特殊性**: 全部实践基于 Codex (GPT-5),未讨论在 weaker 模型上的适用性。是否只有最强模型才能实现这种级别的 Harness 自动化?
- **产品类型局限**: 文章未透露具体产品是什么,难以评估框架在不同类型软件中的通用性。
- **初期成本隐性**: 虽然最终结果是100万行代码,但文章承认早期进展"比预期慢",投入的"环境规格化"工作可能被低估。
- **"不总是匹配人类风格偏好"的妥协**: 文章接受 Agent 生成的代码可能不符合人类风格偏好,这对长期维护和人类介入提出了隐性问题。
- **可推广性存疑**: 文章自身也承认 "This behavior depends heavily on the specific structure and tooling of this repository and should not be assumed to generalize without similar investment"。
- **缺少对失败模式的系统性归纳**: 与 deepset 的四类失败分类法相比,OpenAI 的文章更多是叙事性的,缺乏系统化的分类框架。
