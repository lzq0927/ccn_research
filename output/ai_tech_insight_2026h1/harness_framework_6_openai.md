# OpenAI (Codex) — 百万行代码零手写的Harness Engineering实践框架

**来源**: https://openai.com/index/harness-engineering/
**日期**: 2026-06-05

---

## 一、背景与规模

OpenAI的Codex团队分享了一套在极端规模下验证Harness Engineering有效性的实践框架：

| 指标 | 数据 |
|------|------|
| 团队规模 | 3人起步 → 7人稳定 |
| 开发周期 | 5个月 |
| 代码总量 | ~1,000,000行（约1M行） |
| Merged PRs | ~1,500个 |
| 人均产出 | 3.5 PRs/engineer/day |

这些数字的意义不在于展示"AI多快"，而在于证明：**在几乎没有人类手动编写代码的极端场景下，Harness是唯一保证质量和一致性的手段**。

## 二、7步实践生命周期

### 步骤1：空Git仓库 + Agent生成脚手架

项目从空Git仓库开始，第一个commit由Agent生成整个项目的脚手架代码——目录结构、构建配置、CI pipeline、测试框架。人类只提供高层目标和架构偏好，Agent负责所有实现细节。

### 步骤2：深度优先能力构建

采用深度优先策略构建系统能力：将最终目标分解为一组构建块（building blocks），然后逐个深入完成每个构建块，确保每个组件在被其他组件依赖之前就已经被充分验证。

### 步骤3：渐进式上下文披露（AGENTS.md）

Codex团队引入了**AGENTS.md**文件作为Agent的"上下文目录"：
- 不是百科全书式的文档，而是一份精心策划的目录，指向Agent需要了解的关键信息。
- 随项目增长持续演进，保持对当前最重要的上下文的聚焦。
- 避免了将整个代码库塞进Context Window的低效做法。

### 步骤4：架构机械强制

通过自定义Linters和结构测试将架构规则机械化：
- **自定义Linters**：检查模块依赖方向、文件命名约定、import规则、日志格式一致性。
- **结构测试**：验证目录结构、模块边界、API接口签名符合架构约束。
- 架构规则不再存在于文档中，而是作为可自动执行的检查被强制实施。

### 步骤5：Agent-to-Agent审查

Codex团队最具颠覆性的实践——**完全取代人工代码审查**，改为Agent审查Agent：
- 一个Agent提交PR，另一个Agent审查PR。
- 审查Agent检查代码质量、架构符合性、测试覆盖、性能影响。
- 审查意见以结构化评论的形式反馈给提交Agent。

### 步骤6：持续GC清理

Agent的高产出带来了代码漂移（code drift）的挑战——生成的代码可能在后续迭代中变得冗余或过时。Codex团队部署了持续GC（Garbage Collection）机制：
- 定期扫描死代码、未使用的import、过时的配置。
- 自动生成清理PR，由Agent审查后合并。
- 将"代码卫生"从人工维护转为自动化流程。

### 步骤7：全自动功能交付

最终目标是实现从单一Prompt到完整功能交付的全自动化流水线：
```
单Prompt → 复现（Reproduce） → 修复（Fix） → 验证（Verify） → 合并（Merge）
```
人类只需描述需求，Harness驱动整个交付流程。

## 三、关键机制详解

### Ralph Wiggum Loop

以《辛普森一家》中"做事不走寻常路"的角色命名的循环机制：
1. Agent审查自己刚生成的变更。
2. 如果不满意，Agent请求另一个Agent审查。
3. 根据审查意见迭代修改。
4. 重复直到所有审查通过。

这一机制的关键洞察是：Agent可以同时扮演生产者和审查者的角色，通过自我反思和多Agent交叉审查来提升质量。

### Per-worktree App Booting

每个Codex实例（运行在独立的Git worktree中）启动自己的隔离App实例：
- 避免了多个Agent共享同一个运行环境带来的干扰。
- 每个实例有独立的数据库、缓存、配置。
- 实例的生命周期与任务绑定——任务完成后自动销毁。

### Chrome DevTools Protocol（CDP）

对于涉及UI变更的任务，Codex利用CDP进行自动化UI验证：
- **DOM快照**：在变更前后捕获DOM结构，进行diff比较。
- **截图对比**：视觉回归检测。
- **导航验证**：自动测试关键用户流程，确保UI功能正常。

### 本地可观测性栈

每个worktree运行一个临时的可观测性栈：
- **LogQL**：临时日志查询服务，Agent可以用自然语言查询执行日志。
- **PromQL**：临时指标查询服务，Agent可以检查性能指标。
- 所有遥测数据随worktree销毁而清理，不留生产痕迹。

### 分层架构强制

通过Harness强制执行严格的分层架构：
```
Types → Config → Repo → Service → Runtime → UI
```
每层只能依赖其下方的层，违反依赖规则的代码无法通过Lint检查。

### Taste Invariants（品味不变量）

超越功能正确性的质量标准，将"好的代码品味"编码为可自动检查的规则：
- **命名规范**：变量、函数、文件名的命名风格一致性。
- **文件大小限制**：单文件不超过指定行数，超过则触发拆分建议。
- **结构化日志**：所有日志必须使用结构化格式，包含request_id、timestamp等标准字段。
- **静态强制**：所有Taste Invariants通过自定义Lint规则静态检查，不依赖人工判断。

### Linter错误消息作为上下文

一个精妙的设计决策：Linter的错误消息不仅仅是"报错"，而是包含修复指南的自描述信息。例如：
```
ERROR: layer_violation: UI module imports from Types module directly.
FIX: Route all cross-layer access through the Service layer.
See: docs/architecture/layers.md#dependency-rules
```
这种设计使得Agent在收到Lint错误后可以自主修复，无需人类介入解释错误含义。

### Doc-gardening Agent

专门负责文档维护的Agent：
- 扫描代码库中的文档，检测过时或不一致的内容。
- 自动打开修复PR，更新受影响的文档。
- 确保代码和文档始终同步。

## 四、生产洞察

### "无聊"技术优先

Codex团队有一个明确的技术选型原则：优先选择成熟、稳定、"无聊"的技术，而非新奇、前沿的方案。原因很简单——Agent遇到的问题越少，Harness需要处理的边缘情况就越少。稳定性高于创新性。

### Agent吞吐量远超人类注意力

当Agent每天产出3.5 PRs/engineer时，人类根本无法逐行审查每一行代码。这催生了一个反直觉的经济学洞察：**纠正成本低于等待成本**。与其让人类花时间审查然后发现一个小bug，不如让Agent快速提交、Harness自动验证、发现问题时Agent立即修复。速度比完美更重要。

## 五、框架评价

### 优势

- **实践验证**：1M行代码、1500个PRs的规模是所有Harness框架中最有说服力的实证数据。
- **Agent-to-Agent审查**完全取代人工审查是一个大胆且成功的实践，证明了Harness在质量保障上可以达到甚至超越人类审查的效果。
- **AGENTS.md**作为渐进式上下文披露的机制简洁实用，解决了"给Agent多少上下文"这一关键问题。
- **Linter错误消息作为上下文**的设计体现了"为Agent优化开发体验"的新思维方式。
- **Per-worktree隔离**确保了Agent之间的零干扰，是大规模Agent并行开发的基础设施。

### 不足

- **"无聊技术优先"**可能限制了技术创新的空间，在某些快速演进的领域（如AI本身）可能不适用。
- **对团队规模的依赖**：虽然声称3-7人团队，但这3-7人需要具备极强的Harness工程能力和架构判断力。这种人才的稀缺性可能限制了框架的普适性。
- **缺少对失败案例**的讨论——1500个PRs中一定有Harness未能捕获的问题，这些"逃逸"的案例及其根因分析对框架的改进至关重要。
- **Ralph Wiggum Loop**的终止条件不够明确——如何避免Agent陷入无限审查循环？缺少对审查收敛性的讨论。
