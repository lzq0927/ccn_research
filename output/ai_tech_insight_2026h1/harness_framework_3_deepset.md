**来源**: https://www.deepset.ai/blog/harness-engineering
**日期**: 2026-06-05

---

## 一、核心定义

deepset（Haystack框架的创建者）提出了一个深刻的观点：**"Harness不只是支持模型，它根本性地改变了模型被要求解决的任务"**。这一定义超越了将Harness视为"模型助手"的常规理解，指出Harness的真正价值在于任务重构——通过外部化的认知基础设施，将原来困难的问题转化为简单的问题。

### 核心洞察：难题到易题的转化

deepset识别了三种关键的转化模式：

| 原始问题（难） | Harness转化后（易） | 转化机制 |
|---------------|-------------------|---------|
| Recall（从记忆中回忆） | Retrieval（从存储中检索） | 状态持久化 + 向量检索 |
| Improvised Generation（即兴生成） | Guided Execution（引导执行） | 预定义流程 + 模板约束 |
| Ad-hoc Coordination（临时协调） | Governed Exchange（规范交换） | 协议 + 角色定义 |

---

## 二、三种认知工作的外部化

deepset的核心理论框架将Agent需要完成的认知工作分为三类，每类都可以通过Harness外部化：

### 2.1 State over Time（跨时间状态管理）

**问题**：LLM是无状态的——每次调用都是独立的，无法自然地记住"之前做了什么"。当Agent需要跨多个步骤维护状态时，依赖Model的in-context recall能力是不可靠的。

**Harness解决方案**：将状态持久化到外部存储，将recall问题转化为retrieval问题。Agent不再需要"记住"之前做了什么，而是从结构化存储中"查找"之前做了什么。这一转化将一个认知难题（回忆）变成了一个工程问题（检索）。

### 2.2 Procedural Expertise（程序性专长）

**问题**：让Model即兴生成正确的操作步骤序列是不可靠的——它可能会跳过关键步骤、执行顺序错误或遗漏边界条件。

**Harness解决方案**：将最佳实践编码为可执行的流程定义，将improvised generation转化为guided execution。Agent沿着预定义的流程图执行，每个步骤的输入输出都有明确的规范。

### 2.3 Interaction Structure（交互结构）

**问题**：多个Agent或Agent与外部系统之间的无结构交互容易导致信息丢失、协议不一致和死锁。

**Harness解决方案**：通过定义清晰的协议和角色，将ad-hoc coordination转化为governed exchange。每个参与者知道自己的职责边界，交互遵循预定义的消息格式和时序约束。

## 三、Harness作为统一协调层

deepset将Harness定位为协调Memory、Skills、Protocols三个模块的统一层：

- **Memory**：状态的持久化与检索（对应State over Time）
- **Skills**：工具和能力的注册与调度（对应Procedural Expertise）
- **Protocols**：交互和协调的规范与执行（对应Interaction Structure）

Harness的价值不在于这三个模块中的任何一个，而在于它们之间的协调——确保正确的信息在正确的时间以正确的格式到达正确的处理节点。

## 四、四类失败分类法

deepset最重要的实践贡献是提出了一套系统化的失败分类法，将Agent的所有失败归入四个互斥类别：

### 4.1 Context Failure（上下文失败）

**症状**：Agent缺少完成任务所需的信息——不知道关键事实、遗漏了约束条件、无法访问相关代码。

**根因**：检索逻辑不完善、上下文窗口管理不当、知识库覆盖不足。

**改进方向**：优化RAG检索策略、改进上下文压缩算法、扩展知识库覆盖面、实现更智能的上下文选择逻辑。

### 4.2 Constraint Failure（约束失败）

**症状**：Agent做了不该做的事情——违反安全策略、超出权限范围、忽略编码规范。

**根因**：护栏不足、权限控制不严格、缺少自动化的规范检查。

**改进方向**：加强Guardrails、细化权限控制、添加Linters和静态分析工具、实现更严格的输入输出验证。

### 4.3 Verification Failure（验证失败）

**症状**：Agent的输出看似合理但实际上是错误的——幻觉事实、生成有bug的代码、提供错误的分析结论。

**根因**：缺少独立的验证层、过度依赖Model的self-assessment能力。

**改进方向**：构建测试套件、添加格式验证器、使用LLM-as-judge进行独立评估、实现自动化回归测试。

### 4.4 Planning Failure（规划失败）

**症状**：Agent朝着错误的方向前进——选择了错误的解决方案策略、陷入无效的循环、在低价值任务上浪费资源。

**根因**：编排逻辑缺陷、缺少子Agent委派机制、环检测不足。

**改进方向**：改进编排逻辑、实现子Agent委派、添加环检测和自动策略切换、引入任务优先级评估。

## 五、改进循环

deepset提出了一个简洁但强大的持续改进循环：

```
Run → Observe → Classify → Update → Repeat
```

1. **Run**：让Agent在Harness中执行任务。
2. **Observe**：收集完整的执行遥测数据，包括每一步的输入、输出、决策和结果。
3. **Classify**：使用四类失败分类法对每次失败进行归因——是上下文问题、约束问题、验证问题还是规划问题？
4. **Update**：根据分类结果针对性地更新对应的Harness组件。
5. **Repeat**：持续循环，不断改进。

这一循环的强大之处在于将"改进Agent"这一模糊目标转化为具体的、可操作的工程任务——每次失败都有明确的分类和对应的改进方向。

## 六、Haystack实现映射

deepset将理论框架映射到Haystack框架的具体实现特性：

- **Progressive Tool Disclosure**：根据任务阶段动态暴露工具，避免工具过多导致Model选择困难。
- **ConfirmationStrategy**：可配置的确认策略，支持自动确认、条件确认和强制人工确认。
- **OpenTelemetry + Langfuse**：标准化的可观测性基础设施，支持分布式追踪和性能分析。
- **Pipeline YAML序列化**：将整个Harness配置序列化为声明式YAML，支持版本控制和复用。
- **子Agent隔离**：每个子Agent运行在独立的执行环境中，防止状态污染。
- **多模型路由**：根据任务特征选择最合适的模型，优化成本和性能。

## 七、关键数据

- **Terminal Bench**：研究发现，仅改变Harness（不改变底层Model）就可以让Agent的排名变动20+位。这一数据有力地证明了Harness对Agent性能的决定性影响——甚至在某些场景下超过了模型选择的重要性。

## 八、框架评价

### 优势

- **四类失败分类法**是本框架最大的贡献，它为Agent失败提供了一个系统化、互斥且穷尽的分类体系，将"调试Agent"从一门玄学变成了一个工程过程。
- **三种认知外部化**的理论抽象深刻而优雅，为理解Harness的价值提供了认知科学层面的解释。
- **改进循环**简洁实用，将"持续改进"从一个口号变成了一个可执行的工作流。
- **Haystack实现映射**将理论落地为具体的产品特性，展示了从概念到工程的完整路径。

### 不足

- **四类失败的边界**在某些实际场景中可能模糊——一个失败可能同时涉及上下文和规划问题。框架缺少处理交叉分类的指导。
- **对多Agent场景**的讨论不够深入，特别是多Agent之间的失败如何归因。
- **Terminal Bench数据**虽然有力，但需要更多的跨领域、跨规模的验证数据来支持通用性结论。
