# 根技术 2：结构因果先验（Structural Causal Prior via Topology Graph）

> **一句话本质**：在分布式系统里，"结构"（谁连谁、谁部署什么、谁调用谁）是**先验已知的**。把它做成一张主动维护的拓扑图，就能把"宇宙所有可能故障"压成"拓扑上可达的有限因果路径"。

如果 [01 反证优先](01_反证优先_Falsification-First.md) 解决的是"怎么判"，本根技术解决的是**"在哪搜"**。没有它，LLM 会在无限假设空间里乱猜；有了它，假设只能沿拓扑边生长。

---

## 1. 理论谱系：Pearl 的因果阶梯

### 1.1 因果的三层抽象（Judea Pearl 的 Ladder of Causation）

| 层级 | 问题 | 能力 | 对应故障定位 |
|---|---|---|---|
| L1 **关联（Association）** | "观察到 X，P(Y) 是什么？" | `P(Y \| X)` | "DB CPU 高时，延迟也高" —— 相关 |
| L2 **干预（Intervention）** | "如果我做 X，Y 会怎样？" | `P(Y \| do(X))` | "如果重启连接池，延迟会降吗？" —— 试验 |
| L3 **反事实（Counterfactual）** | "如果当时没做 X，Y 还会发生吗？" | `P(Yₓ \| X', Y')` | "如果没部署那次 config，checkout 还会延迟吗？" —— 反事实归因 |

**关键论点**：纯数据（纯统计）只能爬到 L1。要从相关爬到因果（L2/L3），必须有**结构**——即一张描述"谁影响谁"的有向无环图（DAG），也就是结构因果模型（SCM）的骨架。

AWS 的 Topology Graph 就是这张 DAG 的工程实体。

### 1.2 为什么"结构"是先验，而非数据里学出来的

因果发现（causal discovery）有个根本困难：** observational data 只能给出马尔可夫等价类（Markov equivalence class）**，无法唯一确定因果方向。比如三个变量两两相关，单凭数据分不清是 A→B→C 还是 A←B←C——它们的统计性质相同。

要破这个对称性，必须引入**外部先验**：

- **时序先验**（A 早于 B）→ 见 [03 时间因果](03_时间因果约束_Temporal-Causality.md)。
- **结构先验**（架构上 A 调用 B，不可能 B 调用 A）→ **本根技术**。

在分布式系统里，这个结构先验是**免费且精确**的——因为架构是设计出来的，调用关系、部署血统、资源依赖都能从 CloudFormation/CDK/CI-CD/运行时拓扑里直接读出来。这是分布式系统相对一般因果发现问题的**结构性优势**：不需要从数据里猜 DAG，DAG 本来就在配置和观测里。

> **AWS 的设计选择（母文档关键设计选择）**：Topology Graph 是**主动构建**的（"understanding-your-agentspace" skill 持续维护），不是调查时临时搜的。这一句决定了它能否作为"先验"——先验必须在推断之前就位。

---

## 2. 它要解决的根本问题：无限假设空间

### 2.1 没有结构先验的 LLM 会怎样

给 LLM 一个告警"checkout 延迟"，让它猜根因。没有拓扑约束时，它的假设空间是**所有曾见过的故障模式**——包括与当前系统完全无关的（DNS 劫持、CPU 硅老化、光缆被挖断……）。这导致：

- **幻觉因果**：把两个统计相关但架构不连通的东西连起来。
- **无法证伪**：因为假设空间无限，[01 反证优先](01_反证优先_Falsification-First.md) 的"穷尽反证"在计算上不可行——你无法对"宇宙所有故障"逐一证伪。
- **无法评估 blast radius**：不知道谁连谁，就不知道一次变更会炸到谁。

### 2.2 结构先验做了什么

拓扑图把假设空间裁剪成**图上可达的因果路径**：

```
告警节点 = checkout-service
沿拓扑边向外走（依赖、被依赖、同主机、同部署批次……）
→ blast radius 内的候选节点 = {checkout-svc, payment-gw, db-pool, cache, config-deploy-20min-ago, ...}
→ 假设只能在这些节点上生成
```

这就把 [01](01_反证优先_Falsification-First.md) 的"穷尽反证"从无限空间变成了有限空间——**反证检验在计算上变得可行**。这是根技术 2 对根技术 1 的奠基性支撑。

### 2.3 反模式：临时搜索 vs 主动构建

很多 RCA 工具在调查时才去"搜依赖关系"。问题：

- **延迟与噪声**：调查时现搜，搜到的依赖既不全也不新（有人手动加了实例没登记）。
- **无法做 blast radius 预评估**：Mitigation 阶段需要"改这个会影响谁"，临时搜来不及。
- **无法做 Prevention 聚类**：跨事件学习（根技术 6 的前提）需要稳定的节点身份，临时搜出的节点身份漂移。

AWS 选择**主动维护**——用一个 skill 持续把"现实"同步进图，调查时只读不搜。这是把图当"先验"而不是"证据"的关键。

## 3. 机制内核：一张多源融合的活图

### 3.1 Topology Graph 的数据来源（四源融合）

| 源 | 提供什么 | 性质 |
|---|---|---|
| **CloudFormation / CDK 静态分析** | 声明式依赖（谁引用谁、谁挂载谁） | 静态、精确、但不含运行时实情 |
| **Resource Explorer + 标签** | 资源身份、归属、环境隔离 | 空间/组织结构 |
| **Application Signals / Dynatrace / Datadog 运行时拓扑** | 实际调用关系、流量、延迟 | 动态、真实、但可能含瞬时噪声 |
| **GitHub / GitLab CI-CD 部署血统** | 谁、什么时候、部署了什么版本 | 时间 + 版本（连接到 [03](03_时间因果约束_Temporal-Causality.md)） |

四源合在一起，得到一张同时携带**空间结构**和**时间/版本属性**的多重图。静态源给"应该怎样"，运行时源给"实际怎样"，二者的差异本身就是一个强信号（配置漂移）。

### 3.2 图的边类型（因果语义不同，必须区分）

```
  depends_on        ── 静态依赖（A 引用 B 的资源）
  calls             ── 运行时调用（A 向 B 发了请求）
  co_located        ── 共享宿主（同 host/同 AZ/同 K8s node）
  deployed_together ── 同一次部署批次
  shares_resource   ── 共享连接池/配额/缓存
```

每条边的因果强度不同。`calls` 是强因果（A 慢→B 被拖慢），`co_located` 是弱因果（只在宿主故障时相关）。**反证检验时，假设必须沿"足够强"的边生成**——这就是为什么 H1（config 变更）被秒淘汰：config 到 checkout 之间没有强因果边，只有一条 logging 的弱边。

### 3.3 两处共用同一张图（这是设计的精妙处）

> **诊断和恢复共用同一份结构先验**（母文档根技术 2 的工程实现第 3 条）。

- **诊断侧**：假设沿拓扑边生成、反证沿拓扑边检验（H1 因"拓扑不可达"被淘汰）。
- **恢复侧**：Mitigation 前用同一张图评估 blast radius——"如果我把连接池上限调高，会影响谁？会不会和别的共享 pool 的服务抢资源？"

这种"一图两用"消除了诊断与恢复之间的表示鸿沟：**Agent 不需要把"因果结论"翻译成"变更影响"，因为两者本来就是同一张图上的推理**。这是相比"诊断用一个模型、回滚用另一个模型"的显著工程简化，也避免了翻译过程中的信息丢失。

### 3.4 与因果发现的形式对应

把 Topology Graph 看作一个**带约束的 DAG**：

- 节点 = 资源/服务。
- 边 = 因果方向（A→B 表示 A 可能 cause B 的故障）。
- 拓扑**不连通** ⟺ 因果方向**不存在** ⟺ 假设**直接排除**。

这正是 [08 CausalFusion](08_CausalFusion_AAAI2026.md) 里 LLM 提出的"候选 DAG"在工程上的固化版——区别是 CausalFusion 让 LLM 现场提 DAG 再用统计证伪，而 AWS 把 DAG 提前固化进 Topology Graph，省掉了"提 DAG"这一步的不确定性。两套做法共享同一个内核：**结构约束因果搜索**。

## 4. 在 AWS DevOps Agent 中的具体落地

| 环节 | 拓扑先验的体现 |
|---|---|
| **Context Acquisition** | 告警进来，沿拓扑向外走，标定 blast radius（"这次故障可能涉及哪些节点"）。 |
| **Investigation** | 假设只能在 blast radius 内生成；反证检验时，"拓扑不可达"是最强的反证之一（案例 H1）。 |
| **Mitigation** | 执行建议前，用拓扑评估 blast radius（改这个会炸到谁？）。 |
| **Prevention** | 跨事件按"共享拓扑节点"聚类——三个表面无关的事件若都触及同一 DB 子图，归为同一根因族。 |

母文档交叉验证矩阵的第 4 条规则——**"拓扑可达性是空间约束：不连通则不构成因果候选"**——就是本根技术在判决层的位置。

## 5. 工程实现清单

- [ ] **主动维护而非临时搜**：设一个常驻 skill/同步任务，持续把 4 源数据融合进图；调查时只读。
- [ ] **区分边类型与边权**：不要把所有依赖等权对待；`calls`/`depends_on` 强，`co_located`/`shares_resource` 弱。
- [ ] **节点身份稳定**：用不可变 ID（ARN / commit hash / 服务名+版本），保证跨事件可聚类（支撑 [06](06_可验证情景记忆_ERRORPROBE.md)）。
- [ ] **静态 vs 运行时差异监控**：声明态与实态的 diff 本身是告警源（配置漂移）。
- [ ] **blast radius API**：提供"给定变更，影响哪些节点"的查询，让 Mitigation 和诊断共用。
- [ ] **版本/时间属性上边**：每条边携带最近变更时间戳，直接喂给 [03 时间因果](03_时间因果约束_Temporal-Causality.md)。
- [ ] **图新鲜度指标**：监控"最近一次成功同步到现在"的间隔，新鲜度退化本身就是可靠性风险。

## 6. 失效模式与边界

### 6.1 图过时（最常见的失效）

主动维护依赖同步链路，一旦链路断了，图停留在旧状态。此时拓扑先验变成**错误的先验**——比没有先验更危险，因为它会**自信地排除真因**（真因节点恰好是图里还没登记的新实例）。**对策**：新鲜度指标 + 调查时回退（如果同步间隔超阈值，在结论里标注"拓扑可能不全"，把 `root cause` 降级为 `hypothesis`）。

### 6.2 隐式依赖不在图里

最危险的一类：A 和 B 共享一个**未登记**的底层资源（同一段光缆、同一个 NAT 网关、同一个共享配额）。图上它们不连通，但实际强相关。此时拓扑先验会**错误地排除**真正的共因。**对策**：把"共享底层"也建模进图（根技术 2 的边类型 `shares_resource`）；对"拓扑不连通但时间高度同步"的告警对，单独标记为可疑。

### 6.3 动态拓扑（弹性环境）

在强弹性的环境（频繁 autoscale、serverless），运行时拓扑每分钟都在变。静态图跟不上。**对策**：区分"稳定层"（架构依赖、组织边界，慢变，做先验）和"瞬时层"（实例级调用，快变，做证据不做先验）。先验只用稳定层。

### 6.4 拓扑≠因果（相关性陷阱）

图上有边只表示"可能因果"，不保证"必然因果"。A calls B 不代表 B 慢一定拖累 A（可能有超时熔断）。把"有边"当成"有因果"会过度生成假设。**对策**：边权 + 反证检验联合（[01](01_反证优先_Falsification-First.md)）；拓扑给候选，反证做筛选，两者不可互相替代。

### 6.5 跨账户/跨组织盲区

拓扑图通常局限在一个账号/一个集群。跨组织调用（第三方 API、对等连接）往往是图外的。这类故障会被系统性漏掉。**对策**：显式标注图的边界（"本图覆盖范围 = ..."），对边界节点的故障贴 `hypothesis` 而非 `root cause`。

## 7. 可迁移性：网络 / 系统场景

- **网络设备拓扑**：把 Topology Graph 换成"物理拓扑 + 逻辑拓扑 + 控制面拓扑"三层图。光层（光纤段）+ MAC/IP 层 + 路由协议层（BGP/OSPF 邻居）。一个端口 down，沿拓扑向上追溯到所有受影响的业务路径。**网络场景天然结构化，是本根技术最契合的领域之一。**
- **数据库依赖图**：表级（外键、视图依赖）+ 会话级（锁等待图）+ 存储级（共享表空间）。慢查询定位时，沿锁等待图找阻塞源头。
- **微服务 / service mesh**：与 AWS 场景同构，可直接用 Istio/Linkerd 的拓扑作为运行时源。
- **Kubernetes**：Pod→Service→Deployment→Node→AZ 的层级图，加上亲和/反亲和约束，blast radius 评估特别有效。

迁移时换的是**图的节点/边语义**；"主动维护、区分边权、诊断与恢复共用、用作假设空间的先验裁剪"这套设计原样可用。

## 9. 一句话回到本质

> **分布式系统的因果结构是免费且精确的先验——把它做成一张主动维护的活图，假设空间从无限坍缩为有限，反证检验从不可行变为可行，诊断与恢复共用同一份表示。这是 Agent 不在"宇宙所有故障"里乱猜的根本原因。**
